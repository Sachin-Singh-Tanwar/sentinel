# Sentinel — SPEC

**One line:** A data pipeline that detects when a public source drifts, and proves any repair against a fixed golden set before it is trusted.

**Why it exists:** Every scraper breaks. Most pipelines hide it. Sentinel makes the breakage, the fix, and the proof visible in one incident record.

---

## 1. What it is / what it is not

**Is:** a monitored extraction pipeline over public sources, with drift detection, gated repair, versioned extractors, and an incident log with MTTR.

**Is not:** anti-bot bypass, logged-in scraping, CAPTCHA solving, proxy rotation, personal-data resale, or "an LLM that magically fixes anything".

If a feature requires defeating a protection mechanism, it is out of scope.

## 3. Schemas

Every source has a versioned schema in `schemas/<source>.v1.json`:

```json
{ "id": "books.v1",
  "fields": {
    "title":  {"type": "string", "required": true},
    "price":  {"type": "number", "required": true},
    "rating": {"type": "enum", "values": ["One","Two","Three","Four","Five"], "required": true},
    "stock":  {"type": "integer", "required": false},
    "url":    {"type": "url", "required": true}
  }
}
```

**A2 reconciliation (owner-locked 2026-11-26):** `rating` is **REQUIRED** and `stock`
is **OPTIONAL** for `books.v1`. This supersedes the earlier `stock: required: true`
example and the capture script's `rating`/`stock` optional list. The four handover
fixtures contribute their own partner-verified field sets; together these are the only
schemas used by `golden.load()`. No silent alternate schema is retained.

| schema | required fields | optional fields |
|---|---|---|
| `books.v1` | `title`, `price`, `rating`, `url` | `stock` |
| `hn.v1` | `title`, `url` | `rank`, `points` |
| `gh.v1` | `repo`, `stars` | `language`, `pushed_at` |
| `apify.v1` | `title`, `owner` | `total_users`, `pricing_model` |
| `remoteok.v1` | `position`, `company` | `tags`, `date` |

Rules:
- `required: true` fields participate in the drift score and must be non-null in a golden record.
- A record that fails type or enum validation counts as a **schema failure**, not an empty row.
- An optional field may be null; when present it must still satisfy its declared type.
- Schema changes are additive-only within a major version; breaking changes create `v2`.

---

## 4. Golden set (the core idea)

`fixtures/<source>/golden.json` — **20 archived records per source**, captured once, frozen, committed.

Purpose: a repair is not "probably fine". A repair is accepted only if it reproduces the golden set.

Golden records are never regenerated by the running system. Regenerating them would let a broken extractor certify itself.

---

## 5. Drift detection — signals and thresholds

Evaluated after every run, over the last 50 records unless stated:

| signal | condition | state |
|---|---|---|
| `schema_fail_rate` | > 10% | DRIFT |
| `required_null_rate` | > 20% and previous run < 2% | DRIFT |
| `record_count_drop` | < 40% of trailing 7-run median | DRIFT |
| `empty_streak` | 3 consecutive runs with 0 records | DOWN |
| `http_fail_streak` | 3 consecutive non-2xx | DOWN |
| otherwise | — | HEALTHY |

One state per source. The worst triggered signal wins.

---

## 6. Repair loop (gated, revertible)

```
1. capture      snapshot the failing response (html/json) -> runs/<id>/snapshot
2. propose      candidate extractor (heuristic first, LLM second)
3. evaluate     run candidate against fixtures/<source>/golden.json
4. gate         field_accuracy >= 0.95  AND  no previously-passing field regressed
5. apply        pass -> new version id, incident -> resolved, diff stored
                fail -> nothing applied, incident -> NEEDS_HUMAN, candidate stored
6. revert       any version id can be restored; revert is one command
```

Non-negotiable: **the model never decides.** The golden set decides. The LLM only proposes candidates.

---

## 7. States and MTTR

```
HEALTHY --drift--> DRIFT --repair--> REPAIRING --gate pass--> VERIFIED --> HEALTHY
                                                   \--gate fail--> NEEDS_HUMAN
```

- `drift_detected_at` = timestamp of the run that first raised the state above HEALTHY.
- `verified_at` = timestamp of the run that passed the gate.
- `MTTR = verified_at - drift_detected_at`.
- MTTR is reported only for resolved incidents. Open incidents show elapsed time, labelled **ongoing**.

## 8. API surface

| method | path | purpose |
|---|---|---|
| GET | `/health` | per-source state, last run, drift score |
| GET | `/runs?source=&limit=` | run history with counts and failures |
| GET | `/incidents` | incident list, newest first, with state and duration |
| GET | `/incidents/:id` | full record: timeline, before/after selector diff, golden-set report, MTTR |
| POST | `/admin/inject-drift` | demo only — breaks one source deliberately |

`inject-drift` writes `staged: true` on the resulting incident. The UI must render a **STAGED DEMO** badge on every incident where `staged = true`.

---

## 9. UI (3 screens)

1. **Board** — one row per source: state chip, last run (relative), records, drift score, 20-run sparkline.
2. **Incident** — timeline, the selector/extractor diff (before → after), golden-set pass table per field, MTTR.
3. **Method** — plain language: the five signals, the thresholds above, and the limitation paragraph from §10, verbatim.

---

## 10. Public limitation copy (goes on the site as written)

> Repairs are verified against a fixed golden set. A layout the golden set has never seen can still pass and still be wrong — those cases need a human. Sentinel will not log in on your behalf, will not bypass bot protection, and will not collect or resell personal data.

---

## 11. Non-goals

- No proxy rotation or IP reputation evasion
- No CAPTCHA solving
- No account/login automation
- No scheduling of third-party terms-violating traffic
- No dashboard feature beyond the three screens above

---

## 12. Stack

- Python 3.11, `httpx`, `lxml`/`selectolax`, SQLite (WAL)
- FastAPI for the API
- React + Vite + Tailwind for the dashboard
- Runs with `systemd` on any Linux host; no Docker requirement
- Frontend deployable as static build; API deployable anywhere with a URL

**Amendment (authoritative): Playwright is NOT required for v1.** All five sources are
plain HTTP / HTML / JSON. Do not install browser binaries. If a future source needs a
rendered DOM, it becomes a separate opt-in extra, not a default dependency.

## 13. Build order (for the implementing agent)

1. `books` source end-to-end, golden set, drift on injected breakage
2. gate + revert + unit tests for both pass and fail paths
3. `/incidents/:id` payload with diff and golden report
4. dashboard: Board, then Incident, then Method
5. remaining 4 sources (config only — no new code paths)
6. staged-injection demo path + badge

Do not start step 5 before step 2 passes its tests.

## 14. Build and deploy directive (authoritative)

**Development environment: the local Windows machine. No Codespace. No VM.**

Reasons, so this is not re-litigated:
- The VM has 11 GB disk free and no swap, and it terminates 2026-12-21. It is a build
  host for other work, not a home for this project.
- A Codespace requires an extra OAuth scope and has an unverified core-hour cap.
  Neither is worth spending a blocking step on.
- Nothing here needs a container. Python venv + Node for the dashboard is enough.

**Where each piece runs:**

| Piece | Where | Notes |
|---|---|---|
| Backend source, tests, gate logic | local Windows, `venv` | `< 250 MB`, no browser binaries |
| Dashboard build | **GitHub Actions** (`actions/setup-node` → `npm ci` → build → Pages) | nothing builds on the VM |
| Public demo data | GitHub Actions scheduled run → `data` branch JSON | append-only, same pattern as Tally |
| Dashboard hosting | GitHub Pages | durable, survives VM death |
| FastAPI process | local for dev; optional hosted later | **the public demo must not depend on a live server** |

**The rule that matters:** the public demo is static + Actions-driven. If the API is down,
the demo still loads. Do not build a demo that dies when a machine dies.

`.github/workflows/` is expected to fail to push from a token without `workflow` scope.
Check `gh auth status` first; if the scope is missing, stop and report instead of
deleting the workflow file.
